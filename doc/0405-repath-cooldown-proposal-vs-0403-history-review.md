# 0405 - "재탐색 쿨다운/Unreachable 상태" 참고자료 검토: 과거 이력 및 [[0403]]과의 비교 (제안 검토)

**날짜:** 2026-08-04

**검토 완료 - 사용자가 "현재 상태 유지"를 선택. 코드 변경 없음.**

## 요청 내용

사용자가 "도달 불가능한 목표 추적 개선 방안" 참고 문서를 제시. 요지:

> 현재 `AttackOrderTick()`에서 매 프레임 목표 위치를 갱신하고 `MoveAgentTo()`를 호출 [...]
> 스타크래프트는 이런 경우 매 프레임 재탐색하지 않고 일정 시간 간격으로만 다시 시도한다.

제안된 방식: ① 재탐색 쿨다운(0.5~2초 타이머), ② 실패 횟수에 따라 쿨다운 지수 증가, ③ 마지막 실패
위치 캐싱, ④ 명시적 `Unreachable` 상태 추가(2초 대기 → 재탐색 → 실패 시 다시 대기), ⑤
`NavMeshPathStatus`(PathInvalid/PathPartial) 활용.

## 조사 결과 - 이 프로젝트에서 이미 한 번 겪은 이력

이 참고자료가 제안하는 방식(시간 기반 쿨다운 + 실패 카운트 + 거리 진행도 감시를 조합한 "스타크래프트식
다중 신호")은 **이번 세션에서 이미 [[0395]]로 제안되어 구현됐다가, 사용자 본인이 직접 되돌린 이력이
있다**:

1. [[0392]]/[[0393]]: 3초 재탐색 타이머 도입.
2. [[0394]]: 사용자가 직접 "3초마다 재탐색을 빼줘" 라고 요청 - 타이머 게이트를 완전히 제거하고
   "도착 이벤트에서만 재확인" 방식으로 되돌림.
3. [[0395]]: 사용자가 지금과 거의 동일한 스타크래프트 참고자료(Path Exists / Distance Progress /
   Stuck Timer / Repath Count 조합)를 제시해서 구현.
4. [[0396]]: 그 중 "재탐색 3회 누적 시 포기" 판정을 임시로 꺼서 비교.
5. [[0397]]: 사용자가 그 비활성화 상태("대상이 계속 움직이는 한 절대 포기 안 함, 완전히 멈췄을
   때만 즉시 포기")를 **"이 버전이 제일 좋은거 같네 이대로 마무리하자"** 라며 최종 확정. 타이머/
   진행도 감시/재탐색 횟수 카운트 코드는 전부 죽은 코드로 판단되어 **삭제**됨.

즉 지금 코드(`UpdateUnreachableChase`)에 타이머나 카운트가 하나도 없는 건 빠뜨린 게 아니라, 사용자가
직접 써보고 비교한 뒤 의도적으로 걷어낸 결과다.

## 조사 결과 - 참고자료가 지적하는 증상은 [[0403]]/[[0404]]에서 이미 다른 방식으로 해결됨

참고자료가 문제로 지적하는 것: "매 프레임 NavMesh 경로 재탐색 → CPU 낭비 + 유닛이 멈칫거림". 이건
**이번 대화 앞부분에서 이미 겪고 고친 문제**다(어제 날짜 기준 최근 작업, [[0403]]/[[0404]]).
`UpdateUnreachableChase()`가 도착(또는 더 갈 수 없어 멈춤) 후 대상이 계속 움직일 때 무조건
`MoveAgentTo()`(무거운 `SetDestination`+`SamplePosition`)를 반복 호출하던 게 원인이었고, 지금은:

```csharp
if (targetMoved)
{
    bool reachableNow = IsPositionReachable(targetPos);
    bool wasReachable = !lastMoveAgentToDestination.HasValue || IsPositionReachable(lastMoveAgentToDestination.Value);

    if (reachableNow || wasReachable)
        MoveAgentTo(targetPos, false); // 재탐색 또는 가장 가까운 위치로 1회 이동

    return false; // 이미 도달 불가 상태 유지 중이면 여기서 끝 - MoveAgentTo 자체를 안 부름
}
```

`IsPositionReachable()`은 `NavMesh.CalculatePath()`로만 확인하는데, 이건 에이전트의 실제 경로/이동
상태를 전혀 건드리지 않는 순수 조회라서(`SetDestination`처럼 경로를 리셋하지 않음) **매 프레임
불러도 멈칫거림이 생기지 않는다.** 무거운 `MoveAgentTo()`는 "도달 가능해졌을 때" 또는 "방금 막
도달 불가로 전환된 순간" 딱 그 경우에만 실행된다.

## 참고자료 항목별 비교

| 참고자료 제안 | 목적 | 지금 코드의 대응 |
|---|---|---|
| 재탐색 쿨다운 타이머 (0.5~2초) | 매 프레임 무거운 재탐색 방지 | `IsPositionReachable()` 게이트로 이미 방지됨 - 무거운 `MoveAgentTo()`는 상태 전환 시점에만 호출 |
| 실패 횟수에 따른 쿨다운 증가 | 반복 실패 시 시도 빈도 줄이기 | 애초에 "이미 도달 불가 유지 중"이면 재시도(무거운 쪽) 자체를 안 함 - 늘려야 할 간격이 없음 |
| 마지막 실패 위치 캐싱 | 같은 위치 재탐색 방지 | `lastMoveAgentToDestination` + `RedundantDestinationEpsilon`(0.5m)로 이미 존재 ([[0386]]) |
| 명시적 `Unreachable` 상태 + 2초 대기 | MoveAgentTo/CalculatePath 자체를 호출 안 하는 구간 만들기 | `CalculatePath`는 애초에 멈칫거림을 안 만들어서 "호출 자체를 막을" 필요가 없음. 굳이 만들면 [[0397]]이 걷어낸 상태 필드/타이머 구조가 되살아남 |
| 장시간 도달 못하면 포기 | 무한 추격 방지 | [[0397]]에서 "대상이 완전히 멈추면 즉시 포기, 움직이는 한 계속 쫓는다"로 이미 확정 - 시간 제한을 따로 두지 않는 게 사용자가 최종 선택한 동작 |

## 권고

참고자료의 방향(시간 기반 쿨다운/재시도 카운트/명시적 상태 머신)은 **이미 한 번 이 프로젝트에서
시도됐다가 사용자가 직접 비교 후 더 단순한 방식이 낫다고 판단해 되돌린 설계**이고, 참고자료가
실제로 지적하는 증상(매 프레임 무거운 재탐색으로 인한 CPU/멈칫거림)은 이번 세션 [[0403]]/[[0404]]
에서 타이머 없이 이미 해결됐다. 이 위에 쿨다운/카운트/명시적 상태를 추가로 얹으면:

- [[0397]]에서 "죽은 코드"로 판단해 삭제했던 것과 같은 종류의 필드/상수/상태 관리가 다시 생기고,
- "대상이 움직이는 한 절대 포기하지 않는다"는 [[0397]]의 확정 동작이, 카운트나 타이머 기반 포기
  조건으로 바뀌면서 깨질 수 있다.

**현재 상태(0403/0404) 그대로 유지하고 추가 변경은 하지 않는 것을 권한다.**

다만 참고자료 중 이 프로젝트에 아직 없는 것 하나는 있다: "장시간(예: 수십 초) 도달 못하면 포기"
- 지금은 대상이 계속(아주 조금씩이라도) 움직이면 시간 제한 없이 영원히 쫓아간다. 이게 실제
플레이 중 문제로 느껴진다면(예: 대상이 계속 배회하는데 도달 불가 지형이라 영원히 헛돌아 이상하게
보이는 경우) 별도로 다뤄볼 수 있다.

## 결론

사용자가 "현재 상태 유지 (권장)"를 선택. [[0403]]/[[0404]] 로직을 그대로 두고 참고자료의
쿨다운/카운트/명시적 상태 머신은 도입하지 않는다. 코드 변경 없음.
